# 0134 — ndr markdown adapter uses fence-split → eemeli/yaml → Zod as a layered parse pipeline

## Decision

The `ndr` markdown adapter parses atoms in three layers — a hand-rolled ~25-LOC fence splitter, eemeli/yaml's `Document` AST as the YAML engine, and Zod `safeParse` as the validation/type boundary. The Zod schema also derives the `Atom` TypeScript type via `z.infer` so there is no parallel TS interface.

## Commitments

- `yaml@2.9.0` is a runtime dep; zero transitive deps so the cost is contained.
- `AtomValidationError` surfaces `file` + `issues: { path, message }[]` for CLI rendering, not a stringified Zod error blob.
- The write path forces `id` to `QUOTE_DOUBLE` (per-Scalar-node mutation) and `[]` arrays to flow style (per-Seq `flow = true`) to keep the on-disk shape byte-stable across captures.
- The `Atom` type stays `z.infer<typeof FrontmatterSchema>` — no parallel hand-written TS interface.

## Revisit if

- Humans start editing atom files by hand and trip fence edge cases (fence-in-body, comment preservation).
- Schema validation moves to a library that doesn't co-emit types (e.g. a runtime-only validator), so `z.infer` no longer derives the `Atom` type.

## Context

- gray-matter, the obvious off-the-shelf frontmatter parser, is unmaintained and pins js-yaml 3.x, which silently coerces `id: "0042"` to integer 42 — destroying the atom-id grain.
- eemeli/yaml is actively maintained, has zero transitive deps, and its `parseDocument()` returns a lossless AST whose Scalar nodes preserve `QUOTE_DOUBLE`, so `"0042"` round-trips structurally.
- All atoms in the canonical ledger are machine-generated by the ndr CLI — no hand-edited fence weirdness, no comments-in-frontmatter.

## Why

Each layer has one job, and the alternative single-engine libraries are either unmaintained or skip the validation/type-derivation surface the atom-id grain depends on. Layering Zod on top of the eemeli/yaml engine makes the schema the single source of truth for both runtime validation and the static `Atom` type (`z.infer<typeof FrontmatterSchema>`), so no parallel interface drifts. The hand-rolled fence split stays ~25 LOC precisely because atoms are machine-generated — fence-in-body edge cases are out of scope.

## Alternatives

- **gray-matter** — rejected: silent integer coercion of `id: "0042"` would break atom-id round-trip on every write, destroying the atom-id grain by construction.
- **Zod without a YAML engine** — not a real alternative: Zod isn't a YAML parser; listed only because someone might reach for it before realizing.
- **Single-engine adapter with no Zod layer** — rejected: loses the `z.infer` type-derivation surface (forcing a parallel hand-maintained `Atom` interface) and loses structured parse errors at the CLI boundary (`AtomValidationError` carrying file + Zod issue path).
